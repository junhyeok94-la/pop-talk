# 인프라 점검 결과

2026-08-09, NCP API로 조회한 실제 상태입니다.
**아키텍처 문서(Notion "2. 아키텍처 설계")와 다른 곳이 있어 정리했습니다.**

조회만 했고 **아무것도 변경하지 않았습니다.** 아래 조치는 전부 담당자 판단이 필요합니다.

| | |
|---|---|
| 조회 대상 | `popcorn-vpc` (VPC no. 145019, KR-1) |
| 조회 방법 | NCP API — `getServerInstanceList`, `getAccessControlGroupList`, `getAccessControlGroupRuleList` |
| 조회 결과 | 서버 8대 · ACG 8개 · 규칙 25건 |
| 2026-08-10 추가 | 서버 7대 직접 접속(IP 확인) · 배치 서버 상태 · DB dev/prd 조회 |

> 문서 쪽 값은 Notion 페이지의 **캡처 이미지**를 읽은 것이라, 아래 "확인 필요"로 표시한 항목은
> 원본 표와 한 번 대조해 주세요. 포트 두 건은 양쪽 모두 또렷해 확실합니다.

## 1. 조치가 필요한 것

### 1-1. bastion의 SSH가 인터넷 전체에 열려 있습니다 🔴

`popcorn-bastion-acg` 인바운드 실제 규칙:

```
TCP  121.134.158.113/32  22   "soohan mac SSH for DBeaver tunnel"
TCP  0.0.0.0/0           22   ← 이 줄이 위 제한을 무의미하게 만듭니다
```

특정 IP만 허용하려고 첫 줄을 넣은 것으로 보이는데, 두 번째 줄 때문에 효과가 없습니다.
공인 IP **101.79.20.123**의 22번이 지금 전 세계에 노출돼 있습니다.
bastion은 사설 서브넷 전체로 들어가는 유일한 입구라 영향이 큽니다.

**조치:** `0.0.0.0/0` 22번 규칙 삭제.

⚠️ **지우기 전에 확인하세요.** 지우면 `121.134.158.113`에서만 접속됩니다.
지금 다른 곳(사무실, VPN, 다른 팀원)에서 접속 중이면 그 경로가 끊깁니다.
접속이 필요한 IP를 먼저 모아 각각 `/32`로 추가한 뒤 지우는 순서가 안전합니다.

### 1-2. default ACG가 22·3389를 전 세계에 엽니다 🟠

```
popcorn-vpc-default-acg  INBND  TCP  0.0.0.0/0  22
popcorn-vpc-default-acg  INBND  TCP  0.0.0.0/0  3389
```

현재 서버 8대는 전용 ACG를 쓰므로 당장 뚫린 건 아닙니다.
다만 **앞으로 ACG를 지정하지 않고 서버를 만들면 이 규칙이 붙습니다.**
3389는 Windows 원격 데스크톱이라 이 구성(전부 Rocky Linux)에서는 쓸 일이 없습니다.

**조치:** 두 규칙 삭제. 지금 이걸 쓰는 서버가 없어 영향이 없습니다.

### 1-3. PrivateLink ACG에 규칙이 하나도 없습니다 🟡

```
popcorn-private-link-acg (no. 381084)  규칙 0건
```

CLOVA Studio로 가는 PrivateLink(`10.0.3.13`)에 붙은 ACG인데 인바운드·아웃바운드 모두 비어 있습니다.

> **정정 (2026-08-10)** — 처음에는 이것이 임베딩이 0건인 원인이라고 적었습니다.
> **아닙니다.** 배치 서버에서 확인해보니 CLOVA API에는 닿았고, 오히려 호출 한도를
> 초과해 실패했습니다. 자세한 내용은 아래 4장을 보세요.
> 이 ACG가 비어 있는 것 자체는 여전히 확인이 필요하지만 급하지 않습니다.

### 1-4. 서버 8대 모두 반납 보호가 꺼져 있습니다 🟡

`isProtectServerTermination: false` — 실수로 반납해도 막아주는 장치가 없습니다.
실서비스 전에 켜두시길 권합니다.

## 2. 서버 IP 지도 — 문서와 4곳이 다릅니다 🔴

2026-08-10, bastion을 거쳐 각 서버에 접속해 `hostname`으로 직접 확인한 값입니다.

| IP | **실제 서버** | 아키텍처 문서 |
|---|---|---|
| `10.0.3.6` | **popcorn-backend-1** | ❌ 문서에 없는 IP |
| `10.0.3.7` | popcorn-web-1 | ✅ |
| `10.0.3.8` | **popcorn-backend-2** | ❌ backend-**1**로 표기 |
| `10.0.3.9` | popcorn-batch-1 | ✅ |
| `10.0.3.10` | popcorn-was-2 | ✅ |
| `10.0.3.11` | **popcorn-web-2** | ❌ was-**1**로 표기 |
| `10.0.3.12` | **popcorn-was-1** | ❌ was-**2**로 표기 |

**7개 중 4개가 다릅니다.** 특히 `10.0.3.6`은 문서에 아예 없어서 서버가 6대뿐이라고
읽기 쉽습니다. 배포 대상을 IP로 지정할 때 문서만 보면 엉뚱한 서버를 건드립니다.

조회 방법 — bastion(`101.79.20.123`)에 키로 접속한 뒤 각 서버에 `hostname`을 물었습니다.

## 3. 문서와 실제가 다른 곳

### 3-1. 포트 (확실)

| ACG | 문서 | **실제** |
|---|---|---|
| `popcorn-was-acg` | 9090 | **8080** |
| `popcorn-backend-acg` | 9000 | **8000** |

로드밸런서 타겟 포트도 같이 확인해야 합니다.
**API 명세(`docs/openapi.yaml`)는 팀 결정에 따라 문서 기준 9000으로 두었습니다.**
실제를 문서에 맞출지(ACG 수정), 문서를 실제에 맞출지(명세 수정) 정해주세요.

### 3-2. 계층이 네트워크로 분리되어 있지 않습니다

문서상 web / was / backend / batch가 나뉘어 보이지만,
실제로는 **7대 전부 같은 서브넷(`316110`, `popcorn-sbn-app-private`)** 에 있습니다.
격리는 ACG로만 이뤄집니다. 의도한 구성이라면 문제없지만, 서브넷 단위 분리를
전제로 한 정책(NACL 등)을 세울 때 착오가 생길 수 있습니다.

### 3-3. 확인 필요 — CIDR 값

아래는 **실제 조회값**입니다. 문서의 해당 행과 대조해 주세요.

```
popcorn-web-acg      INBND  TCP  10.0.0.0/23             80
popcorn-was-acg      INBND  TCP  10.0.2.0/24             8080
popcorn-backend-acg  INBND  TCP  10.0.2.0/24             8000
popcorn-batch-acg    INBND  TCP  popcorn-bastion-acg     22   (SSH만)
cloud-postgresql     INBND  TCP  10.0.5.0/24             5432  "bastion Subnet"
cloud-postgresql     INBND  TCP  10.0.3.0/24             5432  "App Subnet"
```

web·was·backend·batch 네 ACG 모두 `popcorn-bastion-acg`에서 오는 22번을 허용하고,
아웃바운드는 `0.0.0.0/0 1-65535`로 열려 있습니다(NAT Gateway 경유).

## 4. 임베딩이 0건인 이유 — 확인했습니다

2026-08-10, `popcorn-batch-1`(`10.0.3.9`)에 접속해 조회만 했습니다.

### DB 상태

| | dev | prd |
|---|---|---|
| 영화 | 5,441편 | 5,309편 |
| 임베딩 작업 큐 | `PENDING` 5,438 | `PENDING` 5,309 |
| **임베딩 결과** | **0행** | **0행** |

`FAILED`도 `PROCESSING`도 없이 전부 `PENDING`입니다. **추천 기능이 동작하지 않습니다.**

### 원인 — 두 가지입니다

**1. CLOVA API 호출 한도를 넘겼습니다.** 배포된 코드의 최신 커밋이 이렇게 적고 있습니다.

```
1cf0262  임베딩 워커 수정 (테스트 중 임베딩 api 초과호출 에러 발생,
                          임베딩 api 호출 로직 변경)
```

네트워크가 막힌 게 아니라 **너무 많이 불러서 막힌 것**입니다.

**2. 워커가 상시 실행 상태가 아닙니다.**

```
systemd 서비스   등록된 것 없음
cron            없음
실행 중인 프로세스  없음
```

손으로 돌릴 때만 돌고 끝나면 멈춥니다. 그래서 큐에 5천 건이 쌓여도 아무도 집어가지
않습니다. `batch_runs`의 8/10 15:14 실행도 수동으로 보입니다.

### 지금 손대면 안 됩니다

`.env`가 8/10 16:00, 코드가 16:18에 갱신됐습니다. **담당자가 작업 중입니다.**
워커를 띄우거나 설정을 바꾸면 그분 테스트와 충돌하고, 호출 한도 문제를 다시
일으킬 수 있습니다.

**조치:** 담당자가 호출 로직 수정을 끝낸 뒤, 워커를 systemd 서비스로 등록할지
결정이 필요합니다. 지금처럼 수동 실행만으로는 신규 영화의 임베딩이 계속 밀립니다.

## 5. 백엔드 설계에 영향을 주는 것

### 5-1. Redis가 없습니다 → 리프레시 토큰은 DB에

ACG 8개 어디에도 6379가 없고, 서버 목록에도 캐시 서버가 없습니다.

`popcorn-backend-1/2` 두 대에 내부 로드밸런서가 요청을 번갈아 보내므로,
**서버 메모리에 상태를 두면 1번에서 로그인한 사용자가 2번에서 튕깁니다.**

| | 두면 안 되는 곳 | 두어야 할 곳 |
|---|---|---|
| 리프레시 토큰 | 프로세스 메모리 | PostgreSQL |
| 로그인 실패 횟수 | 프로세스 카운터 | PostgreSQL |
| JWT 서명 키 | 서버마다 다른 값 | 두 대가 **같은 값** |

→ `docs/user-domain-draft.sql`에 `user_refresh_tokens` 초안을 넣어두었습니다.

### 5-2. 인터넷에서 백엔드로 들어올 입구가 없습니다 🔴

공인 IP는 **bastion 하나뿐**입니다(조회로 확인). 문서 기준 공인 로드밸런서
`popcorn-lb-pub1`은 web-1/2의 **80번만** 바라봅니다.

즉 명세의 `https://api.poptalk.kr/admin/v1`이 지금 구성으로는 동작하지 않습니다.
셋 중 하나가 필요합니다.

1. 공인 LB에 backend용 리스너·타겟 그룹 추가
2. web(nginx)에서 `/admin/v1`을 backend로 리버스 프록시
3. admin 화면을 web 서버에 올려 내부에서 호출

**API를 다 만든 뒤에 정하면 늦습니다.**

### 5-3. GitHub에서 배포할 경로가 없습니다 🟠

backend 서버는 공인 IP가 없어 GitHub Actions(외부에서 실행)가 직접 닿을 수 없습니다.
bastion 경유는 GitHub 러너 IP 대역이 넓고 자주 바뀌어 현실적이지 않습니다.

| 방식 | 비고 |
|---|---|
| NCP SourceCommit/Build/Deploy | VPC 안에서 도는 게 전제라 이 구조에 맞습니다 |
| 자체 호스팅 러너 | VPC 안 서버에 GitHub Actions 러너 설치 |

### 5-4. 배포 시 무중단을 위해 헬스체크가 필요합니다

2대를 둔 이유가 무중단인데, 로드밸런서가 각 서버 상태를 알 창구가 필요합니다.
→ API 명세에 **`GET /healthz`** 를 추가해 두었습니다(인증 없음, DB 끊기면 503).
실제 점검 경로는 basePath가 붙어 `/admin/v1/healthz`입니다.

### 5-5. DB가 단일 장애점입니다 🟡

`popcorn-postgresql`이 **Standalone**(2vCPU/8GB, 스토리지 10GB)입니다.
죽으면 서비스 전체가 멈추고 자동 복구가 없습니다.

- 실서비스 전 **자동 백업이 켜져 있는지** 확인 권장
- 영화 5,985편 + 임베딩 + 리프레시 토큰 누적이 10GB에 들어가는지 확인
- 이중화는 비용 문제라 팀 판단

## 6. 시크릿 관리 🔴

**아키텍처 문서 "8-1. DB 정보" 표에 DB 비밀번호가 평문으로 적혀 있습니다.**
Notion 페이지 권한이 팀 전체이거나 링크 공유 상태면 그대로 노출됩니다.

**조치 권장**

1. Notion 표에서 암호 칸 제거
2. 실제 값은 팀 시크릿 저장소 또는 NCP 환경변수로 이동
3. 이미 공유된 상태라면 **비밀번호 교체** 고려

앞으로 서버 8대에 배포를 시작하면 DB 비번, JWT 서명 키, CLOVA API 키가 흩어집니다.
배포 방식(5-3)과 함께 시크릿을 어디에 둘지 같이 정하는 편이 좋습니다.
