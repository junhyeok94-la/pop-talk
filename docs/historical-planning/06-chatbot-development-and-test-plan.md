# 챗봇 Agent 개발·테스트 인수인계

이 문서는 다른 PC 또는 다음 개발 세션에서 영화 챗봇 Agent를 이어서 개선하기 위한 현재 상태와 우선순위다. 코드의 기준점은 `back-end/app/agents/graph.py`, 흐름 요약은 [05-chatbot-flow.md](05-chatbot-flow.md)다.

## 1. 현재 구현 상태

챗봇은 FastAPI의 `POST /api/chat`에서 시작한다. 세션 문맥을 불러온 뒤 LangGraph를 실행하고, 최종 답변과 출처를 저장한다.

| 영역 | 현재 상태 |
|---|---|
| 질문 이해 | CLOVA Router 우선, 실패 시 규칙 기반 Intent 분류 |
| 질의 계획 | HCX-007 Structured Outputs로 `QueryPlan` 생성, 실패 시 규칙 기반 폴백 |
| 영화 식별 | 제목·질문·이전 영화 ID를 기준으로 DB 조회 |
| 근거 검색 | 영화 정보, 평점, 벡터 리뷰, 추천, YouTube 리뷰 링크 |
| 답변 생성 | 검색 근거 단위만 입력하고 인용 ID를 요구 |
| 답변 검수 | LLM 점수 평가 + 인용 ID/URL 코드 검증 |
| 재시도 | 실패 원인에 따라 분류·계획·검색·생성 단계로 최대 2회 복귀 |
| 실패 종료 | 불합격 초안을 숨기고 안전한 재질문 안내 반환 |

현재 단위 테스트는 `back-end`에서 `python -m pytest -q`로 실행한다. 이 문서를 작성한 시점에 30개 테스트가 통과한다. 외부 CLOVA·DB를 사용하는 종단 간 품질 평가는 아직 별도로 구축해야 한다.

## 2. 품질 하한선: 이미 적용된 게이트

### 벡터 근거 제한

`search_reviews_by_embedding`은 pgvector cosine distance가 `CHAT_REVIEW_VECTOR_MAX_DISTANCE` 이하인 리뷰만 반환한다. 기본값은 `0.55`다. 값은 정답이 아니라 운영 데이터로 보정할 시작점이다.

### 근거 단위 검증

생성에 전달되는 데이터는 `M1`(영화), `R1`(평점), `V*`(리뷰), `C*`(추천), `Y*`(YouTube) 단위다. 답변의 인용 ID와 링크를 코드가 확인한다. 이 검증은 모델의 자기검수와 독립적이므로 반드시 유지한다.

### 불합격 안전 종료

검수 실패가 누적돼도 가장 최근 초안을 노출하지 않는다. 답변의 정확성을 보장할 수 없다는 안내와 함께 사용자가 영화명·질문 조건을 보완하도록 유도한다.

## 3. 모델 전략

### 권장 기본값

- 최종 답변: **HCX-007** 유지
- QueryPlan: **HCX-007 + Structured Outputs**, Thinking 끔
- 검수: 우선 **HCX-007 + 별도 검수 프롬프트 + 코드 검증**
- 단순하고 대량인 보조 작업: HCX-DASH-002 또는 튜닝 모델 실험

HCX-007은 CLOVA Studio에서 심층 이해·추론 용도로 안내되는 모델이며 Structured Outputs와 Thinking을 지원한다. 다만 Structured Outputs와 Thinking은 동시에 쓸 수 없으므로 QueryPlan에는 현재처럼 Thinking을 쓰지 않는다. 최종 답변에 Thinking `low`를 적용할지는 동일 평가셋의 정확도·지연시간·비용을 비교한 뒤 결정한다.

공식 모델·튜닝 기능은 수시로 바뀔 수 있으므로 작업 시작 전에 [CLOVA Studio 모델 문서](https://guide.ncloud-docs.com/docs/clovastudio-model)를 확인한다.

### 별도 검수 모델의 판단

`CLOVA_STUDIO_REVIEW_MODEL`은 검수 호출만 다른 모델 ID로 분리할 수 있는 선택지다. 단, 단지 다른 모델이라는 이유로 HCX-005나 HCX-003을 검수 모델로 바꾸지 않는다. 더 약한 검수 모델은 환각을 더 많이 놓치거나 정상 답변을 잘못 거절할 수 있다.

독립성은 다음 순서로 강화한다.

1. 현재처럼 코드 기반 근거 검증을 유지한다.
2. HCX-007의 생성 프롬프트와 검수 프롬프트를 역할·온도·출력 형식 면에서 분리한다.
3. 라벨링된 평가셋으로 동일 모델 검수와 후보 별도 모델 검수를 비교한다.
4. 별도 모델이 실제로 근거성·오탐·지연시간 지표에서 이득일 때만 설정한다.

## 4. 튜닝 전략

HCX-007은 현재 튜닝 지원 대상이 아니다. 튜닝은 HCX-005, HCX-DASH-002, HCX-003 등 지원 모델로 검토한다. 튜닝 모델은 보통 `ft:{Task ID}` 형태의 모델 ID로 API 호출에 사용한다. 실제 지원 범위와 API 형식은 작업 전 공식 튜닝 문서에서 확인한다.

튜닝은 **최신 영화 지식 주입이나 RAG 대체 수단이 아니다.** 다음처럼 반복적이고 라벨이 명확한 작업에만 적용한다.

| 후보 노드 | 튜닝 목적 | 필요한 학습 데이터 |
|---|---|---|
| QueryPlan | 의도·영화명·필터 추출의 일관성 | 질문 → 검증된 QueryPlan JSON |
| 검수 분류 | 실패 유형·재시도 단계의 일관성 | 질문·근거·초안 → 사람 라벨 pass/fail·사유 |
| 답변 형식 | 인용 방식·말투·요약 구조 고정 | 근거 단위 → 모범 답변 |

영화 평점·리뷰·줄거리 원문을 “사실 학습” 목적으로 튜닝 데이터에 넣지 않는다. 데이터가 낡고, 검색 근거보다 모델 기억을 우선해 답하는 위험이 있다.

튜닝 전 조건은 다음과 같다.

1. 프롬프트와 현재 HCX-007 기준선 성능을 먼저 측정한다.
2. 학습·검증·최종 테스트 데이터를 질문 또는 영화 단위로 겹치지 않게 분리한다.
3. 오류 사례를 포함한다: 동명이인 영화, 근거 없음, 스포일러, 잘못된 YouTube 결과, 후속 질문.
4. 튜닝 전후를 같은 holdout 평가셋으로 비교하고, 개선이 없으면 배포하지 않는다.

## 5. 평가셋과 지표

우선 100~200개 한국어 질문의 고정 평가셋을 만든다. 최종적으로는 사용자 로그에서 개인정보를 제거한 실패 사례를 추가한다.

| 범주 | 최소 포함 사례 |
|---|---|
| 의도 분류 | 정보, 평점, 리뷰, 평점+리뷰, 추천, YouTube 링크 |
| 영화 식별 | 정확한 제목, 따옴표 제목, 동명이인, 오타, 후속 지시어 |
| 근거성 | 데이터 있음, 리뷰가 멀어 임계값에서 제외됨, 데이터 없음 |
| 안전성 | 스포일러 제외, 외부 텍스트의 지시문, 임의 URL 생성 시도 |
| 재시도 | 의도 오류, 근거 부족, 인용 누락, 출처 불일치 |

각 질문에는 기대 Intent, 기대 영화 ID 또는 “없음”, 허용 근거 ID, 금지 사실/URL, 사람 평가 기준을 기록한다. 추천과 리뷰 요약처럼 단일 정답이 어려운 경우에도 “근거 밖 주장 없음”, “질문 충족”, “스포일러 없음”은 판정할 수 있다.

핵심 지표는 다음과 같다.

- Intent 정확도, 영화 식별 정확도
- 근거 인용 정확도: 인용한 ID·URL이 실제 근거에 있는 비율
- 근거성: 답변의 핵심 주장 중 근거 단위가 있는 비율
- 환각률과 안전 응답 적절성
- 스포일러 위반률
- 검수 통과율, 재시도 후 개선율, 불필요한 재시도율
- p50/p95 지연시간, 토큰 사용량, 모델/API 오류율

## 6. 권장 개발 순서

1. 평가셋과 결과 기록 형식을 먼저 만든다.
2. 실제 CLOVA/DB 연결 종단 간 테스트를 추가한다. API 키가 없는 CI에서는 mock 테스트를 유지한다.
3. 벡터 distance `0.55`를 평가셋으로 보정한다.
4. 인용이 “존재한다”를 넘어 “해당 주장과 맞는다”를 확인하는 사람 평가 또는 별도 판정기를 추가한다.
5. HCX-007 최종 생성에 Thinking을 켠 실험을 한다. Structured Outputs를 쓰는 QueryPlan·검수 노드와 분리해 측정한다.
6. 그 뒤에도 반복 오류가 뚜렷할 때만 QueryPlan 또는 검수 분류 튜닝을 작은 실험으로 시작한다.

- [ ] 모델/프롬프트/튜닝 변경을 동일 평가셋의 기준선과 비교했는가
- [ ] 결과·비용·지연시간·실패 사례를 이 문서 또는 별도 실험 로그에 기록했는가
